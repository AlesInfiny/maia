# 結合テスト ( ITa ) {#top}

[テスト戦略](index.md#test-strategy) で示した配分のうち、結合テスト ( ITa ) に該当するテストについて解説します。
結合テスト ( ITa ) は、フロントエンドアプリケーションからバックエンドアプリケーションまでを一気通貫にテストします。
このテストを E2E テストと呼びます。
テストツールを利用した自動 E2E テストについて扱い、手動でアプリケーションを操作する E2E テストについては扱いません。

## 結合テストの目的 {#purpose}

- [UT0](unit-test.md) でテストした機能を組み合わせて、ユースケースが仕様通りに実現できることを確認します
- フロントエンドアプリケーションとバックエンドアプリケーションを結合し、ユースケースごとの動作を検証します

## 結合テストで利用するツール {#testing-tools}

上記の目的を達成するため、 AlesInfiny Maia OSS Edition （以降、 AlesInfiny Maia）では以下のテストフレームワークを用いて結合テストを行います。

- [Playwright :material-open-in-new:](https://playwright.dev/){ target=_blank }
    - 実ブラウザーを操作して、ユーザー操作に近い形で E2E テストを実行します。
- [Mock Service Worker :material-open-in-new:](https://mswjs.io/){ target=_blank }
    - テストモードの存在しない外部サービスへの通信をモックするために使用します。
    - 検証対象であるフロントエンド・バックエンドアプリケーション間の通信はモック化しません。

## 結合テストのテスト対象 {#testing-targets}

結合テストでは、フロントエンドアプリケーションからバックエンドアプリケーション、データベースまで、すべてを結合した状態でユースケースの実現を確認します。
開発したアプリケーションは原則モック化せず、完成済みのものを使用してテストします。

[各テストの配分](index.md#test-allocation) で示したとおり、 E2E テストの対象はユースケースのうち下記の 2 種類[^1]に限定します。
自動 E2E テストは実装・実行・保守ともに高いコストを要するからです。
バックエンドアプリケーションの起動、データベースの準備、外部サービスのモックといった準備が必要になります。

1. ハッピーパス（ゴールデンパス）

    テスト対象のアプリケーションにおいて、最も一般的であると判断されるユースケースです。
    EC サイトであれば、「会員が商品を購入する」といったユースケースが考えられます。

1. ネガティブパス（Scary Path）

    テスト対象のアプリケーションの異常系のユースケースのうち、想定外の動作をした場合にリスクの高いユースケースです。
    EC サイトであれば、「会員が商品を購入する」といったユースケースにおいて、外部の決済サービスの不通により購入がエラーになった場合が考えられます。

この 2 種類の共通点は、システムが想定通りの動作をしなかった場合に業務上クリティカルな影響があることです。
それゆえ、自動化に高いコストを支払ったとしても検証するメリットがあります。

## 結合テストの実行方法 {#testing-method}

結合テストは Playwright 上にテストコードを作成し、実ブラウザーを操作してテストを実行します。
テストの実行前に、バックエンドアプリケーションとデータベースを、テストデータを投入した状態で起動します。
テストの事前準備が必要であれば、その作業もテストコードとして実装し、人手のテスト準備が必要ないようにします。

単体テストで確認済みの仕様は、結合テストで改めて確認しません。
アプリケーションの間で結合をしたときの動作を重点的に確認するようにします。

テストコードの実装方法は、[E2E テスト](../../../../guidebooks/app-testing/e2e-testing.md) を参照してください。
