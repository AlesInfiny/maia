# 単体テスト ( UT0 ) {#top}

[テスト戦略](index.md#test-strategy) で示した配分のうち、単体テスト ( UT0 ) に該当するテストについて解説します。
単体テスト ( UT0 ) は、静的テストと動的テストで構成します。
動的テストは、検証する範囲に応じて 4 種類に分けて行います。

| 区分       | 名称                 | 検証対象                                                       |
| :--------- | :------------------- | :------------------------------------------------------------- |
| 静的テスト | 静的テスト           | ソースコード（不具合の原因となる記述や規約違反を検出）         |
| 動的テスト | 単体テスト           | モジュール単位のロジック                                       |
| 動的テスト | コンポーネントテスト | UI・ロジック・コンポーネント間の結合によるコンポーネントの実現 |
| 動的テスト | 機能内結合テスト     | コンポーネントの結合による機能の実現                           |
| 動的テスト | ユースケーステスト   | 機能間の結合によるユースケースの実現                           |

以降、テストレベルとしての単体テスト ( UT0 ) と区別するため、モジュール単位で行う動的テストを「単体テスト」と表記します。

## 静的テスト ( UT0 ) {#ut0-static-testing}

### 静的テスト ( UT0 ) の目的 {#ut0-static-testing-purpose}

- コーディング規約に準拠したソースコードであるか検証し、開発者間でのバラツキを抑制する
- ソースコード内の潜在的な不具合を自動検出し、品質の向上に役立てる
- 型の不整合をアプリケーションの実行前に検出し、実行時の不具合を未然に防ぐ

### 静的テスト ( UT0 ) で利用するツール {#ut0-static-testing-tools}

上記の目的を達成するため、 AlesInfiny Maia OSS Edition （以降、 AlesInfiny Maia）では以下のツールを用いて静的テストを行います。

- [Prettier :material-open-in-new:](https://prettier.io/){ target=_blank }
    - ソースコードのフォーマットを自動的に整形するフォーマッターです。
- [ESLint :material-open-in-new:](https://eslint.org/){ target=_blank }
    - TypeScript のコードを静的に解析し、不具合の原因となる記述やコーディング規約違反を検出するリンターです。
- [Stylelint :material-open-in-new:](https://stylelint.io/){ target=_blank }
    - CSS を静的に解析し、記述ミスやスタイル規約違反を検出するリンターです。
- [vue-tsc :material-open-in-new:](https://github.com/vuejs/language-tools){ target=_blank }
    - TypeScript の型チェックを行い、型の不整合を検出する型チェッカーです。
    - Vue の単一ファイルコンポーネントを含めて型チェックできるように、 tsc を拡張したツールです。

### 静的テスト ( UT0 ) のテスト対象 {#ut0-static-testing-targets}

静的テストは、フロントエンドアプリケーションのすべてのソースコードを対象に行います。

### 静的テスト ( UT0 ) の実行方法 {#ut0-static-testing-method}

IDE および CI ツールを利用して、自動的に各ツールによるテストを行います。
各ツールの報告する警告は、原則コードを修正して対応します。

## 動的テスト ( UT0 ) {#ut0-dynamic-testing}

### 動的テスト ( UT0 ) の目的 {#ut0-dynamic-testing-purpose}

- 機能が仕様通り実装されていることを確認する
- 機能の追加・修正によってデグレードが発生しないことを短時間で確認できる
- 特に業務ロジックを手厚くテストし、重要機能の障害発生率を下げる

### 動的テスト ( UT0 ) で利用するツール {#ut0-dynamic-testing-tools}

上記の目的を達成するため、 AlesInfiny Maia では以下のテストフレームワークを用いて動的テストを行います。

- [Vitest :material-open-in-new:](https://vitest.dev/){ target=_blank }
    - テストランナーとして、自動テストを実行します。
- [Vitest Browser Mode :material-open-in-new:](https://vitest.dev/guide/browser/){ target=_blank }
    - 実ブラウザーまたはヘッドレスブラウザー上でテストを実行し、ブラウザー固有の挙動を含めて検証します。
- [Vue Test Utils :material-open-in-new:](https://test-utils.vuejs.org/){ target=_blank }
    - Vue コンポーネントをマウントし、表示内容やイベント、状態変化を検証するためのテストユーティリティです。

### 動的テスト ( UT0 ) の共通方針 {#ut0-dynamic-testing-policy}

動的テストは Vitest 上にテストコードを作成し、 IDE および CI ツールを利用してテストを実行します。
テストコードは [AAA パターン :material-open-in-new:](https://wiki.c2.com/?ArrangeActAssert){ target=_blank } に従い、どの環境で実行してもテストが成功するように実装します。

4 種類のいずれも、バックエンドアプリケーションとは結合せず、フロントエンドアプリケーションに閉じた範囲で行います。
API 経由のデータ取得や、グローバルな状態など、テスト対象の外部に依存する箇所はモック化します。
バックエンドアプリケーションと結合した検証は、[結合テスト ( ITa )](integration-test.md) で行います。

[各テストの配分](index.md#test-allocation) に従い、下位のテストで検証できることは下位のテストで検証します。
上位のテストで同じ分岐を検証し直すと、実行時間と保守コストが上位の層に偏るからです。

### 単体テスト {#ut0-unit-testing}

アプリケーションを構成するロジックの妥当性を個々のモジュール単位で検証し、設計通り実装されていることを確認します。
たとえば、分岐条件・バリデーションのルール・ API レスポンスから画面へ詰め替える項目・ストアに保存する項目を検証します。

ロジックを持つモジュールはすべて単体テストの対象とし、分岐を網羅するようにテストケースを設計します。
異常系や境界値の組み合わせも、この層で網羅します。
ロジックの正しさが重要になるため、 Vitest のカバレッジ計測機能を用いて、 Branch カバレッジが 80% 以上となるようテストケースを設計します。

テストコードは Vitest のみを用いて実装します。

### コンポーネントテスト {#ut0-component-testing}

機能内の UI・ロジック・コンポーネント間の結合を検証し、コンポーネントが設計通り実装されていることを確認します。
単体テストでは検証できない、描画結果とユーザー操作に対する振る舞いを対象とします。

テストコードは Vue Test Utils でコンポーネントをマウントして実装します。
実ブラウザー操作に近い形で検証するために、 Vitest Browser Mode の [Context API :material-open-in-new:](https://vitest.dev/api/browser/context.html#context-api){ target=_blank } を用います。

!!! info "コンポーネントテスト"
    コンポーネントには、単独ではあまり機能的な意味をなさないため、テストの効果が薄いものもあります。

### 機能内結合テスト {#ut0-intra-feature-integration-testing}

コンポーネントの間の結合の妥当性を検証し、機能が設計通り実装されていることを確認します。
コンポーネントを結合しなければ確認できない、コンポーネント間のデータの受け渡しを対象とします。

テストコードは、機能を構成するコンポーネントを結合した状態でマウントして実装します。
コンポーネントテストと同様に、 Vitest Browser Mode の Context API を用いて実ブラウザー操作に近い形で検証します。

### ユースケーステスト {#ut0-use-case-testing}

画面コンポーネントから機能を呼び出して機能間の結合の妥当性を検証し、ユースケースが実現できることを確認します。
ユースケースごとに、代表的な流れを対象とします。

テストコードは、画面コンポーネントをマウントし、利用者の操作手順に沿って実装します。
コンポーネントテストと同様に、 Vitest Browser Mode の Context API を用いて実ブラウザー操作に近い形で検証します。
